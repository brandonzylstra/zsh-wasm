zsh-wasm — Code Review
======================

**Date:** 2026-07-05
**Reviewer:** Claude (Opus 4.8)
**Scope:** Project-authored source only. Vendored upstream trees
(`zsh-5.9/`, `awk-src/`, `bc-src/`, `sed-src/` implementation files, `web/zsh.js`,
`web/zsh.wasm`) are treated as third-party and reviewed only at their integration
boundaries (the `*_embed.c` / `*_mod.c` glue, the build script, and the JS runtime).

---

1. Overall Assessment
---------------------

This is a genuinely impressive and carefully engineered project. Compiling a real
zsh 5.9 to WebAssembly and papering over the missing `fork()` with a preamble of
pure-zsh shims is a clever architecture, and the execution is unusually disciplined:

- **Isolation is correct.** Every `runZshScript` call runs on a freshly initialized
  WASM module (`web/zsh-worker.js:14-67`), so shell state genuinely cannot leak
  between runs. The pre-warm-next-module-after-each-run pattern is a nice latency win.
- **Security posture is sound.** ANSI-to-HTML conversion escapes `&<>` *before*
  emitting spans, and every style value comes from a fixed lookup table
  (`web/zsh-runtime.js:3-39`). The test harness escapes all interpolated script and
  output text with `esc()` (`web/test.html:979-981`, used at every `innerHTML` site).
  I found no XSS vector in the reviewed code.
- **The build is reproducible and idempotent.** `bin/setup` and `bin/patch-config`
  guard every mutation with a "already patched?" check, so re-running is safe.
- **Owner conventions are respected.** No abbreviated variable names in the
  hand-written JS runtime API; shims use `_`-prefixed locals to avoid clobbering
  user variables, which is the right call inside an injected preamble.
- **Documentation is excellent** — the READMEs, `docs/PLAN.md`, and
  `docs/RUBYCOMPARED.md` are thorough and honest about limitations.

The findings below are refinements, not alarms. Nothing here is a security hole or a
data-loss bug in the common path. Severity reflects impact on correctness,
maintainability, and release hygiene.

2. Findings by Severity
-----------------------

### 🟠 Medium

#### M1 — Shipped TypeScript types contradict the runtime on `TZ`
`npm/index.d.ts:56-57` states:

> `TZ` environment variable has no effect — `date` always uses the browser's local
> timezone (Emscripten delegates `localtime_r` to JS `Date`).

This is stale. The `date` shim (`web/zsh-runtime.js:357-406`) now parses
`TZ=UTC±H`, `TZ=UTC±H:MM`, and `TZ=±HH:MM` into a real offset, and both READMEs
document it correctly (`README.md:455`, `npm/README.md:100`). The `.d.ts` is the
one artifact npm consumers actually see in their editor, so this is the most
user-visible inconsistency in the repo. Update the doc comment to match the READMEs.

#### M2 — Licensing metadata is incomplete for a binary that bundles four projects
The published `zsh.wasm` statically links zsh **plus** OpenBSD sed, one-true-awk,
and Gavin Howard bc. But:

- `npm/package.json:22` declares `"license": "Zsh"` only.
- There is **no `LICENSE`/`COPYING` file tracked anywhere** in the repo
  (`git ls-files | grep -i licen` returns nothing).
- The npm `files` array (`npm/package.json:14-20`) ships no license text at all.

The READMEs credit the upstreams (`README.md:428-430`), which is good faith, but the
distributed npm tarball carries no license texts for the BSD/MIT/Lucent-licensed code
compiled into it. For a package intended to graduate to the unscoped `zsh-wasm` name,
add a `LICENSE` file (or a `SPDX` expression like `Zsh AND BSD-3-Clause AND MIT`) and
include the bundled projects' license texts in the published files. Low effort, real
compliance value.

#### M3 — Nested pipelines can collide on `/tmp/_zpipe_N` temp files
`simulatePipes` (`web/zsh-runtime.js:951`) recurses into subshell bodies
(`:1027`), but `pipeCount` is a per-invocation local. The recursive call restarts its
counter at 0, so a construct like `(a | b) | c` generates an inner
`/tmp/_zpipe_0` *and* an outer `/tmp/_zpipe_0`. In the traced execution order the
result usually survives by luck (the inner group completes before `c` reads), but it
is fragile and will misbehave for deeper nesting or when a subshell's own pipeline
output must coexist with the outer stage. Consider threading a shared counter (or a
unique prefix per recursion depth) through `simulatePipes` so temp-file names are
globally unique. At minimum, document the nested-pipeline case alongside the existing
"known limits" comment at `:946-947`.

### 🟡 Low

#### L1 — `cp`/`mv` shims mangle file contents
`cp() { print -r -- "$(<$1)" > "$2" }` (`web/zsh-runtime.js:355-356`). Reading with
`$(<file)` strips **all** trailing newlines, and `print` re-adds exactly one. So:
- a file with no trailing newline gains one;
- a file ending in multiple blank lines loses them;
- NUL bytes / true binary content are corrupted.

`mv` inherits this because it delegates to `cp`. Also neither supports the common
`cp a b c destdir/` multi-source form or `cp -r`. Given `zsh/files` is compiled in,
consider using `zf_cp`-style primitives or a byte-faithful copy where available, or
explicitly scope these as "text-file, single-source" in the shim table.

#### L2 — `base64` and byte-oriented shims operate on characters, not bytes
`base64` derives byte values via `printf '%d' "'${_in[_i]}"` (`:853`), and
`head -c` / `tail -c` use character slices (`:124`, `:149`). For any non-ASCII input
these produce wrong output because zsh indexes by character, not byte. This is an
acceptable limitation for the target workload but isn't called out in the shim docs;
a one-line "ASCII-only" note would set expectations.

#### L3 — Untracked debug scripts left in the repo root
`get_errors.cjs` and `get_failures.cjs` (Playwright one-off probes) sit untracked in
the project root (visible in `git status`). They duplicate logic already in
`tests/zsh.spec.js`. Either fold them into a `scripts/` directory and track them, add
them to `.gitignore`, or delete them — leaving untracked `.cjs` files in root invites
accidental `git add .` commits.

#### L4 — `hasPipelineOp` and the pipe simulator disagree on what a pipe is
The fork-off diagnostic uses `hasPipelineOp = / \| /` (`web/zsh-runtime.js:938`),
which only matches space-delimited pipes, while `simulatePipes` correctly detects
`a|b` with no spaces. The consequence is narrow (the helpful "pipes need fork"
stderr hint won't fire for `echo x|cmd` when `fork:'off'`), but the two functions
should share one notion of a top-level pipe to avoid drift.

#### L5 — `docs/NPM.md` is stale relative to the shipped version
`docs/NPM.md:19,197-198` still describe the package as unpublished at `0.1.0`
("advance from `0.1.0` to `0.2.0` before first publish"), but
`npm/package.json:3` is at `0.1.4` and `docs/RUBYCOMPARED.md:16` treats it as
published. Per the owner's "update planning docs when tasks complete" rule, reconcile
`docs/NPM.md` with reality (or mark the checklist items done).

### ⚪ Nits / Observations

- **N1 — `web/style.css` appears unused.** No `web/*.html` references it (only
  `logo.svg` and inline styles are used; `index.html` has its own `<style>` block and
  `test.html` is self-contained). If it's dead, remove it; if it's for a future page,
  a comment would help.
- **N2 — Demo depends on the cdnjs CDN for CodeMirror** (`web/index.html:9-10` and the
  three `mode/lint` scripts). The core runtime is fully self-contained, but the demo
  page silently degrades (no editor, no linter) if cdnjs is unreachable or blocked.
  Fine for a demo; worth a note since the project's selling point is "no server /
  offline-capable."
- **N3 — Deploy uploads `test.html` to production** (`.github/workflows/deploy.yaml:33`
  ships all of `web/`). Harmless, but the 1,144-line test harness is now public on
  Pages. Exclude it from the artifact if you'd rather not ship it.
- **N4 — Per-`sleep` `SharedArrayBuffer` allocation.** `web/zsh-worker.js:46`
  allocates a fresh `new SharedArrayBuffer(4)` on every sleep write. Negligible, but a
  single module-level scratch buffer would be tidier.
- **N5 — `wc` word counting is O(n²)-ish** on large inputs due to per-character zsh
  string indexing in the loop (`web/zsh-runtime.js:94-98`). Acceptable for
  cheatsheet-sized inputs; just be aware it won't scale to megabyte files.

3. Category Notes
-----------------

### Correctness
The shims are remarkably faithful for their size. `grep` alone implements
`-i/-v/-n/-c/-o/-l/-q/-w/-A/-B/-C/-m/-e/-r/-H/-h` with context-block merging
(`web/zsh-runtime.js:163-304`) — that's a serious amount of behavior. The main
correctness risks are the byte-vs-character issues (L1, L2) and nested-pipeline temp
collisions (M3), all of which are edge cases outside the documented happy path.

### Concurrency / Worker lifecycle
The worker/pool handoff (`web/zsh-runtime.js:1053-1126`, `web/zsh-worker.js`) is
correct: the result is built from a `capture` reference captured *before*
`startPreInit()` reassigns the module-level `_capture`, and `onmessage` awaits the new
`_moduleReady` before reading `_module`, so it never reads a half-initialized module.
`_busySleepFallback` is read at device-write time, after `onmessage` sets it, so the
option takes effect on the intended run. No races found.

### Build system
`bin/build` and `bin/setup` are the most complex hand-written code here and are well
commented. The re-application of `config.modules` overrides after every `make prep`
(`bin/build:70-84`) shows hard-won understanding of the zsh build. The embedded-tool
approach (compile out-of-tree `.o` files, inject via `LDFLAGS`, hand-write the
`.epro`/`.mdh`) is fragile-by-nature but each step is explained. The `awk` global
renames to dodge symbol collisions (`bin/build:318`) are a good defensive touch.

One robustness note: the three `--with-*` blocks are near-identical ~80-line copies
differing only by tool name. If a fourth tool is ever added, factor the shared
scaffold (config.modules insertion, `.epro`/`.mdh` generation, per-object emcc loop)
into a shell function parameterized by tool name to avoid three-way drift.

### Testing
235–247 in-browser cases plus a Playwright gate (`tests/zsh.spec.js`) is strong
coverage for the shim surface, and the `data-known-fail` mechanism for expected
failures is a clean pattern. Gap: there is **no unit test for `simulatePipes` itself**
— it's pure, string-in/string-out, and holds the trickiest logic in the JS layer
(quote/bracket tracking, subshell recursion, M3). A dozen direct assertions on its
output (including nested pipelines) would catch regressions the end-to-end tests can
miss.

### Security
No injection surface found. Worth restating the one architectural exposure the code
already documents: `$(...)` runs **in-process** (the `exec.c` patch in
`bin/setup:77-139`), so command-substitution side effects and variable mutations leak
to the parent shell. That's inherent to the no-`fork()` design and is clearly
documented (`npm/index.d.ts:50-51`), not a defect — but any future feature that
executes untrusted scripts expecting subshell isolation must account for it.

npm publish.
